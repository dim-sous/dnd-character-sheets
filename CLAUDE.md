# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A D&D 2024 character sheet PWA for a home game. It is a **tracker, not a rules engine** — every field is free-form, nothing is validated, no class features or level-up logic. Derived numbers (modifiers, proficiency bonus, saves, skills, passive Perception, spell DC/attack) are never stored, only recomputed. Vanilla JS, no framework.

## Commands

There is **no build, no bundler, no package manager, no lint step** — and that is a hard product constraint, not a gap to fill. The repo must run from a bare folder.

- **Run locally:** serve over HTTP, never `file://` (a bare file path blocks ES module imports and makes `localStorage` flaky). VS Code Live Server ("Go Live"), or:
  ```bash
  python3 -m http.server 8000
  ```
- **Tests:** `node tools/run-tests.mjs` runs the full suite headless (Node ≥ 22.7 — no browser, no deps, no `package.json`), or open `tests.html` in a browser for the same assertions. The suite lives in `tests.js`, imported by both. No per-test filter — comment others out to isolate one. CI runs the runner on every pull request, so a broken calculation blocks the merge.
- **Deploy:** merge/push to `main` → `.github/workflows/deploy.yml` runs `tools/stamp-sw.py` (stamps the service-worker cache version + precache list from the deployed files), stages the site with `tools/` excluded, and publishes to GitHub Pages. **The artifact is the app, not the repo (#148)**: it used to upload the working directory as-is, which put every probe page on the live origin — and a probe seeds `localStorage` through the app's own key, so opening `/tools/probe.html` on the deployed site replaced the visitor's characters with the audit fixture. The excluded set is `stamp-sw.py`'s `SKIP_DIRS`, deliberately: the precache list has never included `tools/`, so before this the worker and the published site disagreed about what the app was. A hostname guard inside each probe is the wrong shape — a per-file allow-list grows a hole every time a probe is added, which is what #115 settled by suppressing by position. Re-runnable from the Actions tab via `workflow_dispatch`. Production URL: https://dim-sous.github.io/dnd-character-sheets/

## Measuring the running app

**There IS a browser available in this WSL environment — do not assume otherwise, and do not hand a UI check back to the user as unverifiable.** Windows Chrome is reachable through WSL interop, runs headless, executes ES modules and JS, and can be measured. Node also exists even when it is not on `PATH` (the VS Code server ships one).

**In a Linux cloud session the recipe below is the wrong one.** There is no Windows Chrome; `node` is on `PATH`; Chromium lives under `PLAYWRIGHT_BROWSERS_PATH` (`/opt/pw-browsers/chromium-*/chrome-linux/chrome`) with Playwright installed globally. The documented flags got 10 of 15 probes reading `pending` there: virtual time raced to the budget during the non-virtual `serviceWorker.getRegistrations()` / `caches.keys()` teardown every probe does first, so the DOM was dumped before the probe's first real timer was due — indistinguishable from the hung-probe symptom of a JS syntax error, and raising the budget "fixed" it unreliably. The same race lost 5 of 20 runs on this WSL recipe too, four Chromes at a time. Every probe now holds virtual time across that teardown (see the virtual-time trap below), which took it to 0 of 168 here, four at a time — but that has **not** been re-checked in a cloud session, so there, **drive the probes with real wall-clock waiting**: launch Chromium through Playwright, `page.goto`, then poll `#out` until its text stops being `pending`.

```bash
# node, when `node` is not on PATH (this is what runs the test suite)
NODE=$(ls -d ~/.vscode-server/bin/*/node | head -1); "$NODE" tools/run-tests.mjs

# 1. serve the repo (Windows Chrome reaches WSL's localhost directly)
python3 -m http.server 8000 --bind 127.0.0.1 &

# 2. drive Chrome headless and print the page's post-JS DOM
CHROME="/mnt/c/Program Files/Google/Chrome/Application/chrome.exe"
"$CHROME" --headless=new --disable-gpu --no-first-run --no-default-browser-check \
  --user-data-dir='C:\Temp\cc-probe-profile' --force-device-scale-factor=1 \
  --virtual-time-budget=25000 --dump-dom "http://localhost:8000/tools/probe.html"
```

`tools/probe.html` is the standing **usability audit**: it seeds a character through `blankCharacter()`, loads the app in a fixed-width iframe, walks every tab and edit/arrange mode, and reports any control that is under 44px, **not the thing a tap there would actually hit**, owns a pseudo-element that has escaped it, or carries **text under WCAG AA against the colour actually behind it** (see the traps below). Extend it rather than writing throwaway probes. Read its header comment before changing it.

**The audit reads a control's own EDGE, not just its text (#159).** WCAG 1.4.11 asks 3:1 for the boundary of a control, and `probe.html` measured text colours only — which is how an app shipped in which *every* unchecked checkbox painted nothing at all (91 of them, 1.00:1, both themes: the PROF and EXP columns of Abilities & Skills were headers over empty space). The cause was `input:read-only` matching checkboxes — in CSS a checkbox is always `:read-only`, and that rule sat 1550 lines below the base checkbox block at equal specificity. `controlEdgeFailures` now walks every checkbox and radio, takes the border if it is painted and the background if it is not, and composites from the PARENT up: an edge is judged against what surrounds it, not against its own fill.

**A row name that ellipsizes is a decision, not a failure (#154).** `probe.html` measures every cropped text input, but a crop inside a `.row__primary` is reported as a NOTE on the verdict rather than counted as a failure: a spell row is one line by design, because the card is eighteen rows deep and a wrapped row is 96px with two lone controls under a title. Play mode still shows a 28-character name in full; only Edit, where the ✕ joins the line, gives up the last few characters. Everything outside a list row that crops is still a hard FAIL, and the truncation count is printed even on a PASS — an assertion nobody reads is worse than none.

**An unseeded list measures nothing.** A row list with no rows renders one empty-state line, so every control the row contains — its fields, its ✕, its tap targets — is never looked at, and the card reports PASS at all four combos while the thing it exists to show has not been measured once. Seed any list you add, with a short row *and* a deliberately long one: every field in this app is free-form, so "what a real player types" is the load. This is not hypothetical — it is written into the `resources` seed for #140, and adding the #141 spell seed immediately surfaced a 42px textarea and two fields cropping real values (a `.row__detail` textarea had *never* been measured, because nothing seeded features or feats either). Two more ways to measure nothing, both found in #145 and both now a FAIL in `probe.html`: a **mis-keyed seed** (the inventory fixture said `name` where the row binds `item`, so its long value rendered as an empty box from the day it was added; the audit now fails if any string seeded into a list row is not some field's value once the app is up), and a **scene whose card is on another tab** (#164 moved Features to Character, so at 390px its Edit scene measured a `hidden` panel and reported nothing; `edit()` now brings the card's own tab forward, and fails if the card is still off screen).

**Four runs, and all four are load-bearing** — two widths × two themes. Width is a query parameter; the theme is a Chrome flag, and headless defaults to *dark*, so a pair of runs without the flag is two dark runs agreeing with each other:

```bash
for CS in 1 0; do for W in 390 1440; do   # preferredColorScheme: 1 = light, 0 = dark
  "$CHROME" --headless=new --disable-gpu --user-data-dir="C:\Temp\probe-$CS-$W" \
    --blink-settings=preferredColorScheme=$CS --virtual-time-budget=240000 \
    --dump-dom "http://localhost:8000/tools/probe.html?w=$W"
done; done
```

The verdict line names the width and theme it measured, because a PASS that doesn't say which one it was is worth very little: #115 hit both widths at different rows and either alone reported PASS at the other, and #118's accent failures existed only in dark.

Each reseeds `localStorage` — including the layout keys, which are `dnd-character-sheets:layout` and `:layout-default`, colons not hyphens — so runs don't inherit each other's mutations.

- `probe-detail-rows.html` — the reveal control on the rows whose hidden half is a block of fields (#147: `.row--feature`, `.row--feat`, `.row--spell`). Edit mode no longer force-opens them, so a card of eight features is not a page of scrolling, and the affordance is a real `.row__expand` button rather than a `::after` caret — a pseudo-element cannot be tabbed to, cannot carry `aria-expanded`, and cannot be given a 44px target without covering the ✕ beside it. The checks that earn their place: **`elementFromPoint` on both buttons** (two 44px boxes on one line is the geometry #115 got wrong), `aria-expanded` tracking BOTH ways in (the button and the play-mode tap-anywhere gesture go through one `setRowExpanded`, or they drift), a tap on the name field in Edit typing instead of folding the row, and the width trade — a short row must not wrap, a long name must not be cropped by the buttons.

Two consequences worth knowing before touching it: `.is-prepared` is maintained by `renderDerived`, never `renderSheet` (ticking Prepared is a derived change, and a structural render on every tick is the #146 bug), and printing is now one `@media print` rule instead of a `beforeprint` handler — `probe-spells.html` asserts that rule is *parsed*, which is the guard against the unbalanced-comment trap below. **Play mode STARTS every level but Cantrips collapsed** (the owner's call, 2026-10-21): the tab opens on what is ready, always-prepared spells included, and Cantrips open because a collapsed Cantrips section shows every row anyway (`renderSpells`, keyed off `canPrepare`). - `probe-spell-picker.html` — the SRD spell picker (#149). Holds the claims the pure suite cannot reach: that the 330KB library is **not** fetched at boot and is on first open (read off `performance.getEntriesByType('resource')` — a stray static import would undo the whole point and break nothing visible), that a pick round-trips through `state.addRow` with every field filled, that a spell files itself by **its own** level rather than the section the picker was opened from, that the picker stays open across picks, and that the custom/blank path still works when the library never loads. Also the reason a picker scene exists in `probe.html`: a modal `<dialog>` puts the rest of the document in the top layer's inert shadow, so every audit walk scopes to `dialog[open]` when one is open — measuring the sheet behind it would report every control on the page as "covered", which is the exact shape of the scrim bug the heuristic hunts for.
- `probe-layout-transfer.html` — the layout backup dialog (#162). The pure suite covers the envelope and every refusal; this covers what it cannot see. The checks that earn their place: that the textarea is wired to the **live** layout (the `:layout` key does not exist until the first arrange action, so an export read from storage would be empty on exactly the devices where that is least visible), that each refusal leaves the live tab set **byte-identical** — the catastrophic case being a pasted character backup, which `normalizeLayout` turns into `DEFAULT_LAYOUT`, so a trusting importer reports success while factory-resetting the player — that an import with a **different tab set** still leaves exactly one panel visible with one `aria-selected="true"` (the `reactivateTab` guard; `activateTab` has none, and a dangling active tab is a blank sheet at 390px and a silent PASS at 1440px), that one paste is one Undo step, that Escape on a **button** inside the dialog does not drop the player out of arrange mode, and that the whole thing is reachable with **zero characters** — the fresh-install moment the feature exists for, where `#btn-arrange` is hidden. Note it goes through `#btn-menu` rather than clicking the drawer's buttons directly: a closed off-canvas sidebar is `inert` on purpose, so a direct click measures something no user can reach and focus can never be returned into it. Copy runs against a **stubbed** clipboard (the virtual-time trap below), so every run asserts both answers and the no-API case, that a blocked copy really leaves the text selected as its message says, and that an empty box writes nothing over what the player had copied.
- `tools/sw-update/run.sh` — the service-worker update check, and the one thing here that does NOT use the recipe above. It builds two marked snapshots of the app from the working tree, stamps each exactly as the deploy does, serves them like Pages (`max-age=600`), and has one headless Chrome session install the first, "deploy" the second mid-session and report which files the NEW worker serves. The origin is WSL's own IP made secure with `--unsafely-treat-insecure-origin-as-secure` (the app skips its worker on localhost), and every wait is real time — worker install races virtual time. Three traps it already hit: snapshots built in the same second revalidate as 304 (Last-Modified is to the second); a fetch the active worker is still handling holds back the next worker's activation, so the page's real-time delay is served from another port; and a private-IP page may not load from `localhost` (Private Network Access).

Escape is driven twice on purpose: a scripted keydown reaches the page's listeners but runs no default action, while `requestClose()` takes the real close-request path into the dialog. Traps these probes exist to catch, all of which have produced silently-passing checks here:

- **An unbalanced comment silently deletes the rule beneath it, and every probe still passes.** CSS error recovery skips to the next `{…}` block and discards it, so one stray `*/` above `.row--hitdie, .row--resource` dropped the whole de-slabbing rule — and the Hit Point Dice tile visually reverted to the parchment card-in-a-card it was fixed out of in #65. Nothing caught it: a slab breaks no tap target, no contrast pairing, no overflow, and crops no value. **Where a rule's whole job is to remove a default, assert the computed result** (`backgroundColor` transparent, `padding`/`border` 0) — `probe-resources.html` §3 does this for both rows. The JS twin is worse: a literal `*/` inside a block comment ends it early, and a module with a syntax error never runs at all, so the page prints `pending` and reads like a hung probe rather than a failure. Both mistakes were made in this repo an hour apart; a comment-balance scan over `style.css` and each probe's module is a five-line script and worth re-running after any large comment edit.
- **An unseeded list renders only its empty state, so `probe.html` measures nothing.** A new list tile passes all four runs while the row it exists to show has never been looked at once — the tile is real, the fields are not there yet. #140 shipped its four PASSes that way, and adding two seeded rows immediately failed three scenes at both widths (`"Channel Divinity: Turn Undead" needs 233 in 146`, and 96 once Edit reveals the ✕). **Seed every new list in `probe.html` with a short row and a deliberately long one**, which is the same lesson the attack rows already carry: *"With only `Dagger` in here the probe reported PASS through all of it."* Free-form fields make "what a real player types" the load, not the placeholder.
- **`localStorage` is debounced 400ms.** Reading the store straight after a commit returns the *previous* value. Assert against the DOM (the field, the readout) and only read storage after a wait longer than the debounce.
- **A script-assigned `.value` doesn't set the input's dirty flag**, so no `change` fires and the handler under test never runs — while the probe reports PASS. Type with `document.execCommand('insertText')` instead.
- **A control being the right size does not mean it can be tapped** (#115). An absolutely-positioned pseudo-element whose owner is `position: static` resolves its insets against some ancestor — or, with no positioned ancestor at all, against the initial containing block, i.e. a viewport-sized invisible sheet at the document origin. `.skill__exp::after` was a 44px tap target written for a checkbox; a save row's Exp cell is an empty `<span>` of the same class, so six 397×907 sheets (at a 390px phone; the box is the size of the *viewport*, which is why the dead row differed between phone and laptop) covered every control in the first screenful, in cards the player had never opened. The touch-target audit could not have caught it: an empty spacer span is not a control, so nothing measured it — and asking how big a control is was never going to reveal something sitting on top of it. `elementFromPoint` is the only honest test — it accounts for stacking, `pointer-events` and clipping at once, and it names the pseudo's *owner* as the culprit.
- **Reachability must be sampled at more than one scroll offset, or you measure the furniture.** A fixed/sticky bar covers a band of the *viewport* and is escaped by scrolling (the arrange bar is 489px tall with its disclosure open); an escaped pseudo covers a band of the *document* and is escaped by nothing. Only the second is a bug, and one offset cannot tell them apart.
- **A closed `<details>` is not `display: none` in Chrome.** It uses content containment, so descendants keep stale non-zero rects while being correctly un-hit-testable — 83 controls' worth of confident nonsense, each naming whichever unrelated tile sits at those coordinates. Gate on `closest('details:not([open])')` / `checkVisibility()`, not on a zero rect. The same applies to `pointer-events: none`: arrange mode inerts the sheet that way on purpose, and an intentionally inert control is not a covered one.
- **Virtual time fast-forwards timers, not the browser.** Under `--virtual-time-budget` a `wait(300)` elapses at once, but anything answered across a process boundary — the clipboard, the service-worker registry, `caches` — settles in *real* time. That has failed two ways here. With a timer pending, the probe reads before the answer lands, and the late answer then lands on the NEXT check: `probe-layout-transfer` read Copy's status as `""`, then blamed Download for Copy's "blocked" — a probe that could only pass where waits are real. With no timer pending, virtual time leaps straight to the budget and the page is dumped reading `pending` — the teardown at the top of every probe, see the cloud note above. Both fixes are one rule: **stub an API whose answer you assert**, with one that settles in a microtask (which also lets both answers be asserted instead of "either"), and **keep a timer ticking across an await you cannot stub** — the `hold` interval around each teardown. Measured, an EMPTY tick is not enough: it burns the whole 240s budget in about 0.15s of wall time, which four Chromes starting at once can outrun (1 run in ~80 still read `pending`; none in 168 since). So each tick does about half a millisecond of busy work, which stretches the budget to seconds of real time. A MessageChannel loop does not freeze virtual time either — measured, it advances it.
- **A queued event lands on whatever is open when it arrives** (#124). A `<dialog>`'s `close` event is queued, not dispatched, and under load it was measured arriving AFTER the next question had opened — so an answer that trusted `close` dismissed the second question with the first one's event, about one run in ten (Cancel on Long rest, then Delete: "Delete …?" vanished, answered No). `confirm-dialog.js` resolves on the button's own click and ignores a `close` that finds the dialog open; `probe-confirm.html` cancels one question and asks the next in the same task, which makes the race happen on purpose. That probe failed without the guard and passes with it.

Gotchas, all of them learned the hard way:

- **`--user-data-dir` is required.** Without it Chrome forwards to the user's already-running desktop instance and your flags are silently ignored. One directory per concurrent run; four at a time is fine.
- **Wait until Windows can reach the server, not just WSL.** Localhost forwarding lags a new listener, so a Chrome launched the moment `http.server` starts can fail with `ERR_CONNECTION_REFUSED` (on stderr) and dump an empty page, which a summary script reads as "no output" rather than as a failure. Poll with Windows' own curl first: `/mnt/c/Windows/System32/curl.exe -fs -o NUL http://localhost:8000/`.
- **Headless Chrome reports `prefers-color-scheme: dark` by default**, so anything measured without saying otherwise is the DARK theme — a "light vs dark" comparison run with no flag is two dark runs that agree. Pin it explicitly: `--blink-settings=preferredColorScheme=1` is light, `=0` is dark. Verify with `matchMedia('(prefers-color-scheme: dark)').matches` in the page, because a wrong guess here reads as "both themes pass".
- **Read colours off a canvas, not out of the computed string.** `color-mix(…, transparent)` computes to `color(srgb …)` or `oklab(…)`, so an `rgba()` regex silently fails — and a background that fails to parse looks like no background at all. That is how the "Done" chip's accent tint got skipped and its contrast was measured against the bare card (4.38:1) instead of the tint that actually sits behind it (3.86:1). Paint the value into a 1×1 canvas and read the RGBA bytes back; then composite every translucent layer down to the first opaque ancestor.
- **Don't trust `--window-size` for viewport width** — Windows display scaling distorts it. Pin the width with a fixed-size `<iframe>` instead; that is what `probe.html` does.
- **Use `setTimeout`, not `requestAnimationFrame`, to wait.** Under `--virtual-time-budget` timers are fast-forwarded reliably; an animation-frame loop is not guaranteed to be driven.
- **Probe pages belong in `tools/`, never the repo root.** `tools/` is in `stamp-sw.py`'s `SKIP_DIRS`; a stray `.html` at the root **would** be precached and shipped to every player's phone.
- **Kill the service worker before measuring, or you will measure the last build.** The app registers a cache-first worker, so a probe run in a reused `--user-data-dir` serves stale CSS and stale modules — it shows up as a change that "didn't apply", or a `does not provide an export named …` error for code you just wrote. Every committed probe unregisters it and clears `caches` before loading the app; do the same in any new one, or use a throwaway profile directory. **And the worker is not the only cache in a reused profile.** `python3 -m http.server` sends `Last-Modified` and no `Cache-Control`, so Chrome caches every file heuristically — a file unchanged for days stays "fresh" for hours — and a re-run in the same `--user-data-dir` after an edit can load the PREVIOUS copy of the file you just edited. Seen with `probe-tile-size.html`, which re-ran the assertion it had just been edited out of and printed the old failure. The teardown cannot help: the stale file is the probe page itself, fetched before any of its code runs. Give each run a fresh directory (suffix a timestamp) and delete them afterwards.
- **Inactive tab panels carry `hidden`**, so a control measures 0×0 until you activate its tab. Some controls only exist in a card's edit mode (the spell-slot total is setup-only — play mode renders a count instead — and it is the **Spell Slots** card's Edit that reveals it, not Spellcasting's). `probe.html` puts every `[data-editcard]` card into Edit, reading the list off the page, so a card added later is audited in Edit without anyone adding a scene; before #145, six of the eleven never were.
- **Measure, don't infer.** This stylesheet has a recurring trap where a class rule (0,1,0) declares a size that the base `input[type=…]` / `.icon-btn` rule (0,1,1) outranks, so the control is *not* the size the CSS appears to say. Reading the stylesheet has already put wrong claims into three issues; measurement disproved them. The honest tap target is also not the border box — `.pip` and `.toggle` carry theirs on an absolutely-positioned `::after`, and `.chip` puts it on the wrapping `<label>`.

## Architecture

**Unidirectional loop, single source of truth:**

```
DOM events ─▶ state mutator ─▶ emit() ─▶ subscribed render() ─▶ DOM
                   └─▶ debounced 400ms ─▶ localStorage
```

Event handlers only mutate state and re-render — they never reach into unrelated DOM. Persistence hangs off `emit()`, so no mutator has to remember to save.

**The data layer is strictly DOM-free and must stay that way.** The test suite (`tests.js`) imports every DOM-free module — `constants`, `rules`, `storage`, `state`, `nudges`, `layout`, `layout-registry` — taking only the pure surface of the ones with side-effecting halves (`state.js` mutators and `nudges.js`'s recorders are deliberately untested; see the comments at the imports). That is the whole reason the arithmetic is kept pure and separate, and it is why a module that reaches for `document` can never be tested here:
- `js/constants.js` — `blankCharacter()` (the canonical shape every stored/imported character is merged over), the ability/skill/condition lists, `STORAGE_KEY`.
- `js/rules.js` — every derived number as a pure function (`saveTotal`, `skillTotal`, `characterPB`, `passivePerception`, `spellSaveDC`, `isSpellcaster`, `applyDamage`/`applyHealing`, `formatMod`…). No DOM, no state, no side effects.
- `js/storage.js` — localStorage read/write, normalization/migration (imports are merged over `blankCharacter()` so old or hand-edited files never crash), import/export. `downloadFile`/`today` are exported for the layout exporter (#162) — that is the one sanctioned touch from the layout side, and it is additive: nothing here learns what a layout is. Note "DOM-free" is true of this module's SCOPE only; `downloadFile` is a Blob/anchor path the suite never calls.
- `js/state.js` — the **only** place a character is mutated. Dot-path `getByPath`/`setByPath`; `updateActive(path, value, type)`, `toggleInArray`, `addRow`/`removeRow`, `setSlotsUsed`, `longRest`. `emit(type)` where `type` is `'structural'` or `'derived'`.
- `js/spell-library.js` — the SRD picker's search, ranking and `spellToRow`, as pure functions (#149). Takes the spell array as an argument and never imports it, so nothing drags the 330KB data file into a boot path.
- `js/extra-spells.js` — the table's own additions: spells it uses that the SRD lacks (Summon Beast first), **hand-written** in the SRD entries' shape plus a `source` the picker shows ("PHB 2024"). Loaded beside `spell-data.js` by the same dynamic import and searched as one list. The rule that matters: **never paste a book's text into it** — the site and repo are public and only the SRD is licensed for sharing. Facts and stat-block numbers, SRD boilerplate reused where the SRD has it (the summon spells share Summon Dragon's), and anything else in our own short words. `tests.js` holds every entry to the SRD shape, requires a non-SRD `source`, and refuses a name the SRD already has (the picker would list it twice).
- `js/spell-data.js` — **generated, do not hand-edit.** ~340 SRD 5.2.1 spells, written by `tools/build-spell-data.py`; re-run that rather than patching a spell. Loaded by a **dynamic** import the first time the picker opens (precached by the service worker, so it is offline after that) — a static import anywhere would put the whole SRD in the app's boot path for a feature most sessions never touch, and `probe-spell-picker.html` is the only thing that would notice.
- `js/render.js` — character → DOM.
- `js/spell-picker.js` — the DOM half of the library, as `layout-view.js` is the DOM half of `layout.js`. Owns one `<dialog>` and its filter state; it does not import `state.js` — the caller passes `onAdd`, so the only thing it can do to a character is hand back a row.
- `js/confirm-dialog.js` — the app's one "are you sure?" (#124): `askConfirm({ title, body, confirmLabel, danger })` → `Promise<boolean>`, over the `#confirm-dialog` markup in `index.html`. Like `spell-picker.js` it does not import `state.js`; the caller decides what a Yes does. It resolves on the button's own click, never on the `close` event (see the late-`close` trap), and anything that shuts the dialog without an answer is a No.
- `js/main.js` — delegated listeners, bootstrap, service-worker registration.

A layout/markup change that forces a change to `rules.js`/`state.js`/`storage.js`/`constants.js` is a smell — stop and reconsider. `tests.html` must stay green.

**Rendering is split by trigger rate (this split is load-bearing):**
- `renderSheet(char)` — STRUCTURAL changes only (open a character, add/remove a row, import). Rebuilds sections and writes each `[data-bind]` input's value exactly **once**; after that text fields flow DOM→state only. Rebuilding on every keystroke would reassign `.value` on the field being typed into and throw the caret to the end.
- `renderDerived(char)` — EVERY change. Recomputes `[data-derived]`, re-checks `[data-toggle]`, and writes back `[data-bind]` inputs **except** `document.activeElement` (so it never clobbers the caret).
- `renderSlotPips(char)` — targeted pip rebuild for spell-slot totals, so typing a total doesn't destroy its own input.

**No per-field event handlers.** Three delegated attributes drive everything, so adding a field to `index.html` usually needs zero JS:
- `data-bind="dot.path"` (+ `data-type="number|nullable-number|checkbox"`) — two-way bound field.
- `data-toggle="arrayName"` + `data-value="key"` — membership in a list (proficiencies, conditions).
- `data-action="name"` — dispatched through the `ACTIONS` map in `main.js`.
- `data-structural="true"` makes a field fire on `change` (not `input`) and trigger a structural render.
- A computed readout is `<output data-derived="kind.arg">` plus a `case` in `derivedValue()` calling a pure `rules.js` function.
- Repeatable lists = `data-list` + `<template id="tpl-…">` + `ROW_TEMPLATES` (constants) + `LIST_PATHS` (state) + `ROW_TEMPLATE_IDS`/`renderRows` (render).

**Tabbed layout (added in #6).** The sheet body is five `role="tabpanel"` panels with a `role="tablist"` bottom bar. The tab IDS are `combat`, `abilities`, `spells`, `gear`, `character`; since #164 two of their LABELS no longer match — `combat` is labelled "Status" and `gear` is labelled "Attacks" — because the shipped default is now a real exported arrangement and an id is internal (the `#tab-<id>` / `#panel-<id>` node and the `home` key) while the label is the only part a player sees. Read the label from `TAB_REGISTRY`, never from the id; roving-tabindex arrow-key nav lives in `main.js`, `activateTab`/`syncActiveTab` in `render.js`. Every panel stays in the DOM — inactive ones carry the `hidden` attribute (never render-on-demand, because `renderDerived` walks `[data-derived]`/`[data-bind]` across the whole document). On laptop (≥900px) and in print the tab bar is hidden and `.tabpanel[hidden]{display:contents!important}` reveals every panel at once (multi-column on screen, full sheet on paper). The active tab is not persisted — opening a character lands on the first tab in the layout. Ability scores and saving throws both live on Abilities and are built by one render, `renderAbilities`: each ability group gets its score row plus a `.skill--save` row from `tpl-ability-group`, so a save is a skill row that happens to have no expertise cell (`render.js`). There is no `renderSaves` and no second saves surface anywhere.

**Service worker.** Caches the app shell cache-first. **Each build's precache must be fetched fresh**: `cache.addAll()` went through the browser's HTTP cache, and Pages sends every file with `max-age=600`, so a worker installing within ten minutes of the previous build's fetches stored the PREVIOUS build's files under the NEW build's cache name and served them cache-first until the next deploy — the long-rest change reached a phone that way, old question and nothing refilled, while every file on the live site was correct. `precache()` fetches `url?v=<CACHE_VERSION>` with `cache: 'reload'`, which is new to the HTTP cache and to the CDN alike. `tools/sw-update/run.sh` is the only check that can see this — the app never registers its worker on localhost, so no probe does — and it fails on the old code. `tools/stamp-sw.py` sets `CACHE_VERSION` and the precache list from the deployed files during CI, so you normally do **not** bump the version by hand (the README's manual-bump note predates that automation). An installed PWA still needs a reopen/reload to pick up a new build.

**Storage.** Characters live in `localStorage` under `dnd-character-sheets`, per device, never synced. Export is the only backup and the only way to move a character between devices. **Import asks nothing**: a character is matched by id alone (never by name), a match is updated by `importCharacters`/`keepPlayState` in `storage.js` and keeps the device's inventory, coins, notes and play state, carrying what was *spent* rather than what is left, so a levelled-up file shows its new capacity; anything unmatched is added. The safety net is the banner's Undo, which `state.js` drops on the next `emit()` of any kind. localStorage is scoped to origin (not path) — relevant to preview-deployment work (#8).

**A layout is not in a character export, and now has its own (#162).** The arrangement lives under `:layout` (and a player-set baseline under `:layout-default`), and until #162 it had no backup path at all — a reinstall or a cleared site destroyed it silently, while `nudges.js` was telling the player Export had them covered. The file format is `layoutExportEnvelope`/`serializeLayout`/`parseLayoutFile`/`layoutImportSummary` in `layout.js`, pure and fully covered by the suite; the dialog is in `layout-view.js`. Three things not to undo:
  - **The payload is NESTED under `layout`, not spread across the envelope, and that is a safety property.** With a spread payload `normalizeLayout(parsed)` *works*, because unknown top-level keys are dropped — so skipping the `kind` check yields a feature that passes every happy-path test and silently factory-resets the player's layout when fed a character file. Nested, `parsed.layout` is `undefined` for anything else, so the mistake is unavailable.
  - **`normalizeLayout` can never be the discriminator.** It answers "what is the nearest valid layout to this?" and never "is this a layout?": `null`, `42`, `'garbage'`, `{}`, `{tabs:[]}` and a character backup all come back deep-equal to `DEFAULT_LAYOUT`. Every validation therefore runs *before* it, and the non-empty-tabs guard is the single most important one — it is the one case where a successful import and a factory reset look identical from the outside.
  - **`layoutSchemaVersion` must travel on the same object that reaches `normalizeLayout`, and a newer version is refused rather than best-effort read.** `SPAN_MIN` is 2, which is both a legal v2 span and a v1 key, so a v2 payload read as v1 triples every narrowest tile — silently. The refusal is the opposite of the character path on purpose: a character file may be the only copy of irreplaceable data, while a layout is reconstructible and the import *overwrites* an arrangement the player still has.

  `migrate()` now names `case 2` explicitly instead of letting `default` mean "current". That changes nothing today and is the point: `default` meaning current is only true until the next bump, and a bump to 3 without a `case 2` would read every stored v2 blob as v3 unmigrated — which matters more now that layouts travel as files that outlive the build that wrote them.

**The shipped default is an arrangement someone played with, not a guess (#164).** It was exported from a device through #162's Layout backup and baked into `layout-registry.js`: tab labels, which tab each card is homed to, card order, tile order, tile widths, tile heights and tile names. `tests.js`'s `describe('the shipped default arrangement (#164)')` holds the whole thing as a fixture, so changing what a new player sees means changing that block deliberately rather than drifting into it. Three things to know:

- **`defaultHeight` exists for this.** Before #164 the default could express order, width and naming but not height, so the arrangement the app ships with could not be the arrangement anyone plays with. `normalizeHeight` now falls back to the registry exactly as `normalizeSpan` does. An explicit `0` is still kept and still means "as tall as its contents" — that is what lets the slider clear a height — so only a layout with NO height field picks the default up, which is every layout saved before heights shipped.
- **A fixed height CLIPS, and nothing measures that.** `.tile.is-sized` sets `overflow: hidden`, so a tile shorter than its contents silently cuts them off; `probe.html` measures cropped text inputs, not clipped tiles. The four short tiles ship 2px shorter than their `scrollHeight`, which is box-model slack — the AC input's bottom border is 7px clear. If you change a `defaultHeight`, measure `scrollHeight - clientHeight` and check what is actually in the gap rather than trusting a green audit.
- **A defaults change breaks probes that NAME things, and it reads as a bug in the feature.** #164 broke four: `probe-detail-rows` activated `tab-gear` to find the Features card and got nine "0x0" failures once the card moved to Character (an inactive panel carries `hidden`); `probe-resources` hardcoded the string "Resources"; `probe-tile-size` relied on a missing height meaning 0; and `probe-arrange-fn` hit-tested `#f-hp-current` at a viewport coordinate that stopped being on screen when Hit Points went from first in the card to eighth. The fixes are all the same shape — **derive the tab from where the card actually is, read labels from the registry, pin a fixture's heights explicitly, and `scrollIntoView` before `elementFromPoint`.** `elementFromPoint` takes VIEWPORT coordinates, so a control below the fold resolves to whatever furniture sits at those coordinates and reads as unreachable when nothing is wrong with it.

## Conventions

- **Never add a dependency, build step, or runtime CDN/library.** CI tooling (Python scripts, Actions) is fine — it does not touch the shipped artifact, which stays byte-identical static files.
- **Phone-first**, designed ~375–390px. Minimum 44px touch targets. Real ARIA semantics. Verify UI changes at **390px and 1440px**, and check print preview when layout changes.
- Hidden elements use the `hidden` attribute and depend on the global `[hidden]{display:none!important}` in `style.css` — an author `display` silently beats the UA `[hidden]` rule, which has bitten this app before.
- **Cantrips are never prepared (#158).** In the 2024 rules a cantrip is always known and always available, so a cantrip row shows no Prepared tick, the Cantrips heading reads a plain count rather than "0 of 2", `rules.canPrepare(level)` is the single place that rule lives, and the whole-list `preparedCount` skips level 0. Two consequences: a collapsed Cantrips section is EXEMPT from #155's prepared-only filter (`.spelllevel:not([data-level="0"])`) or it would fold to a bare heading, and the tick is hidden with `visibility: hidden` rather than removed — `renderDerived` reads that checkbox to decide what a collapsed level shows, and the 44px it still occupies is what keeps cantrip names on the same left edge as every other level's. A `prepared: true` already stored against a cantrip is left alone and round-trips untouched; nothing counts it.
- **Always-prepared spells are their own flag, and never count toward the limit.** A spell a subclass, species, feat or item hands you is `alwaysPrepared: true` on its row — a separate boolean, not a third value of `prepared`, so un-flagging gives back whatever the daily tick was. Its row shows a ★ in the tick's 44px column (`.is-always`, set by `renderDerived` beside `.is-prepared`, which it also sets — a ★ spell survives a collapsed level). The ★ is a mark, not a control: the flag is setup data, set in the row's details under Edit and shown there in play only on a flagged row. `rules.preparedCount` excludes flagged spells, because that count is the one compared with the class limit; `rules.preparedSummary` writes the heading sentence ("2 of 4 · 2 always" — the ★ spells leave the denominator too, so all six rows are accounted for) and the card total. Never offered on a cantrip, and a stale flag on one is kept and not counted, exactly like #158's stale tick.
- **The class's prepare limit is `spellcasting.preparedMax`, typed by the player.** It is the class table's "Prepared Spells" column; the app knows no class progression. 0 means "not tracked" (the Max HP contract), and the Spellcasting card's third tile then shows a bare count instead of "4 / 0". Over the limit the count goes `--bad` (`rules.isOverPrepared`) and nothing is refused. The tile centres "4 / 6" on the slash with a `1fr auto 1fr` grid, because the limit's field keeps its 44px box even when flattened (the audit measures every input) and a one-digit limit centred in it read as "4 /   6".
- The behaviors the app encodes (all hand-overridable): damage is taken from temp HP first then real HP and floors at 0; a long rest (confirmed) restores **lost** HP, clears temp HP, death saves and concentration, regains all spent Hit Point Dice (2024 restores the full pool, not half), refills every class resource, drops exhaustion by 1, and resets spell slots. The recovery arithmetic lives in `rules.js` (`restoreHp`, `restoreHitDice`, `restoreResources`, `applyDamage`, `applyHealing`) — never inline in `state.js`, so the edge cases stay testable.
- **Destructive actions ask through `askConfirm()`, never native `confirm()` (#124).** The native box ignores the theme and dark mode and, in an installed PWA, draws system chrome with the origin on it. The cost is that a confirmed ACTIONS handler is `async` and its action lands a microtask after the click — fine for a player, and the reason a probe answers the dialog by clicking rather than stubbing. A handler that blurs a field before asking (Long rest) must blur again after: the dialog hands focus back when it closes.
- **Healing never lowers hit points, and neither does a rest** (`applyHealing`, `restoreHp`). A hand-set current above max is a deliberate override; the largest heal in the game must not be the one that costs you HP, especially while character data has no undo (#107).
- **A Max HP of 0 means "not tracked", never "a ceiling of zero."** Max is Edit-gated and `blankCharacter()` starts it at 0, so noting current HP without ever opening Edit is the ordinary path. `applyHealing` treats an unset max as unbounded and `restoreHp` leaves current alone — resting used to assign max over it and land the player on 0, silently, since the `.is-dying` cue itself requires `max > 0` (#106).
- **Git/PR flow:** branch as `feat/<issue#>-<slug>` (also `fix/…`, `docs/…`); open a PR to `main`; the rules suite (CI) must pass; merge as a merge commit. There is no hosted PR preview — review a PR locally with `gh pr checkout <n>` (see the README); deploys happen on push to `main`.
